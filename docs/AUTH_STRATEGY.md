# Authentication Strategy

Version: 0.1.0
Last updated: 2026-06-04

## Direction

MySkills should own its user model directly. External providers can help users sign in, but local users, roles, registration policy, sessions, MFA state, audit, and authorization remain application-owned.

## Candidate Library

Better Auth is the current candidate for the TypeScript implementation. Its current docs show support for:

- email/password authentication
- email verification and password reset flows
- admin, roles, and permissions plugins
- two-factor authentication
- passkeys
- social providers
- account linking
- database-backed auth with Postgres

This is a planning decision, not a permanent lock-in. The first implementation milestone should spike Better Auth against the selected API/web runtime before committing broadly.

Spike acceptance:

- Works with the Node/Fastify API runtime or has a clean boundary through a dedicated auth handler.
- Uses Postgres without forcing a second canonical user store.
- Supports email/password, verification, password reset, admin/role controls, and two-factor plugins.
- Can coexist with CLI/API token flows.
- Does not make an external provider the source of application authorization.

## Current Foundation Slice

The current API implementation owns the first-party auth boundary directly:

- `users.normalized_email` is the canonical login and uniqueness key.
- Password credentials are stored separately from users and hashed with bcrypt.
- Login creates opaque bearer session tokens; only token hashes are stored.
- Scoped API tokens are generated by the server, stored only as hashes with display prefixes, and returned in plaintext only once.
- Email verification, password reset, registration invitation, and email-change action tokens are short-lived, single-use, hashed in the action-token table, and delivered only through the configured notification sink. The current sinks are Resend, SMTP, and local-development console delivery.
- TOTP MFA stores encrypted authenticator secrets, creates short-lived opaque challenge tokens after password login, marks MFA verification on the resulting session, and stores recovery codes only as hashes.
- Review-scoped API tokens for owner, admin, and maintainer users must be created from an MFA-verified session; review actions require an MFA-verified session or MFA-bound token.
- Registration is controlled by the instance registration setting and currently creates pending users. Email verification sets only the email-verification gate; request-mode accounts still require admin approval before login. Admin invitations create passwordless pending users and activate them only when the invitation token, invited email, pending user, and password creation all match atomically.
- Password reset is generic for account-existence privacy, including delivery failures, rejects unusable accounts, updates the password credential, and revokes existing sessions and API tokens after success.
- A successful password reset, authenticated password change, or email change atomically invalidates outstanding password-reset and email-change links. Reset recipients must match the current account email. Issuance and completion serialize per account and recheck the email and password credential observed before issuing a link or authorizing a password change.
- The newest password-authenticated email-change request supersedes older email-change links when it is stored. Delivery failure does not restore those links because delivery may have occurred before an error; the user can request another link. Public password-reset requests preserve existing links until a security change succeeds, so unauthenticated requests cannot cancel a user's recovery or email change.
- MFA-verified owner/admin sessions can read and update registration mode, manage non-secret provider configs and explicit claim-to-role mappings, list safe user records, and approve, activate, disable, or delete users. User disable/delete revokes existing sessions and API tokens.
- Provider config records store only non-secret metadata. Provider secrets remain deployment secrets, and external provider mappings currently allow only `user`, `author`, and `maintainer`; `owner` and `admin` remain local/manual roles.
- Authorization still uses application roles, not provider claims. Provider mapping changes do not mutate existing local role assignments.

This keeps setup portable for the open-source project while leaving room to adopt Better Auth or another provider adapter for passkeys, provider MFA, and account linking once the web runtime is in place.

## Public Auth Notification Outbox

Public email-verification and password-reset request routes commit an action token and an encrypted delivery intent together under the account lock. Their existing `202 {status:"pending"}` response no longer waits for SMTP or Resend. The configured rate limits still apply before token issuance. This removes provider-dependent response latency; it does not make account lookup and database work constant-time. Registration verification, admin invitations, and authenticated email changes retain their existing synchronous delivery contracts.

The dedicated `auth_notification_outbox` stores an AES-256-GCM payload containing only the token and recipient email. A versioned, purpose-separated key is derived from `AUTH_SECRET`; authenticated metadata binds the payload to its job ID, token hash, and purpose. User records and password hashes are never serialized into the payload. Keep `AUTH_SECRET` consistent across API replicas. Rotation makes pending payloads unreadable: the worker discards them, and affected users must request new links. Backups can retain encrypted token material until the backup retention period ends.

Each API process runs one nonoverlapping worker. A transaction claims at most ten due intents using `FOR UPDATE SKIP LOCKED`, commits a 60-second lease, then releases all database locks before provider I/O. Lease IDs fence recipient checks and completion updates. A worker rechecks token expiry/use, current recipient, and account eligibility before delivery. It never creates a replacement token from an old intent. R1 password/email changes remain authoritative; a change racing after the pre-send check can deliver an unusable link, but cannot restore its validity.

Delivery retries use the same token, with at most five claimed attempts and backoff starting at 30 seconds. Token TTLs remain one hour for password resets and 24 hours for verification. A worker waits at most 15 seconds per provider call; Resend receives a cancellation signal, and queued SMTP sends own an isolated transport that closes on cancellation and has finite connection, greeting, and socket timeouts. Acceptance followed by a crash or uncertain transport result can produce duplicate mail. Delivery is at least once while retries remain eligible, with no exactly-once or eventual-delivery guarantee. Successful, invalid, expired, and exhausted intents lose their encrypted payload immediately; batches remove terminal rows older than 24 hours. Cleanup progresses while the configured worker runs.

Shutdown stops new claims, cancels provider waits, and bounds worker drain to 20 seconds before pool closure. Unfinished leases are recovered by a later worker. No provider error text or notification payload is logged by the worker; dispatch failure logs use a fixed message. The existing development-only console sink intentionally prints action links and remains prohibited in production.

Apply migration `0031_auth_notification_outbox.sql` before starting this API version. For rollback, first stop issuance and dispatch on every replica. Drain pending intents with this version, or explicitly discard them and accept that users must request fresh links, before reverting to synchronous delivery. Keep the additive table until queued work is resolved. Do not run old and new dispatch policies concurrently during rollback.

The shared memory and disposable-Postgres outbox cases cover historical mixed-case display emails, provider-barrier response independence, HTTP contracts, usable positive-control tokens, atomic insertion rollback, lease fencing/recovery, retry/expiry limits, R1 invalidation, payload confidentiality, and bounded shutdown. These checks are required before release; source implementation alone is not runtime or delivery evidence.

## Required Product Behavior

### Registration

Admins can choose:

- closed registration: admins invite users
- request registration: users request access and admins approve
- open registration: anyone can register, optionally restricted by email domain

Every registration path should support email verification and audit events.

### Authentication

Required:

- email and password
- email verification
- secure password reset
- session management
- logout from current session and all sessions
- rate limiting on login, registration, reset, MFA, and token endpoints

Recommended for first public release:

- TOTP MFA
- recovery codes
- passkeys as optional second factor or passwordless sign-in

### Authorization

Use application roles and scopes:

- `user`: browse and install visible approved skills
- `author`: create private drafts and submit packages
- `maintainer`: review submissions and approve releases in assigned scopes
- `admin`: manage users, settings, provider mappings, and global lifecycle actions
- `owner`: initial instance owner with break-glass controls

Provider groups, Cloudflare Access claims, OIDC claims, or SAML attributes can map into local non-admin roles only through explicit admin configuration. `owner` and `admin` are not granted from external provider claims in the current foundation.

### API And CLI Tokens

Current CLI login uses first-party email/password prompts, completes MFA challenges with a TOTP or recovery-code prompt, and stores the returned session token locally by normalized API URL. Browser-based device or authorization-code login remains the preferred future provider flow where possible.

Token rules:

- store CLI tokens by API URL so local, staging, and production credentials do not cross over
- use user-only local file permissions for the current default token store
- move CLI tokens to the platform secret store by default when that backend is added
- support token revocation and rotation
- expose token names, scopes, last used time, and expiry in account settings
- never store provider refresh tokens on the CLI
- use short-lived access tokens plus refresh or session-bound tokens where practical
- require both local role authorization and token scopes for protected API, CLI, and MCP operations
- require an interactive session, not an API token, to create, list, or revoke API tokens

### Cloudflare Integration

Cloudflare should be optional:

- Cloudflare Access can protect an instance or admin area.
- Cloudflare Access identity can map to a local user after verification.
- Cloudflare Turnstile can protect public registration and reset flows.
- Cloudflare R2 can be an object storage option.
- Cloudflare Workers can be a deployment target if framework and auth constraints fit.

No Cloudflare feature should be required for the core open-source app.

## Auth Verification Checks

- Email/password signup, verification, login, logout, and reset tests.
- Admin registration modes tested for allow and deny paths.
- MFA setup, challenge, recovery, disable, and lockout tests.
- Provider mapping tests for unmapped, mapped, downgraded, and revoked identities.
- CLI token tests for storage, refresh, revocation, and scope denial.
- API, web, and MCP authorization parity tests.
